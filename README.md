# opencode-localcat

It was not hand-written line by line. The code passes `tsc --noEmit` type checking and builds cleanly (`npm run build` produces `dist/`), It now targets the opencode 1.x plugin API (`{ id, server() }` + the `config` hook) and has been verified end-to-end against real llama.cpp / litellm / workbuddy-wild backends. Issues and PRs are welcome.

OpenCode plugin that auto-discovers models from **llama.cpp**, **LiteLLM**, and **workbuddy-wild** backends and exposes them as first-class OpenCode providers. It pulls the model list from each backend's OpenAI-compatible `/v1/models` endpoint, then enriches every entry with capability metadata (context window, max output tokens, tool/vision/reasoning support) by querying each backend's extended metadata endpoint:

> Repository: <https://github.com/lucky2you/opencode-localcat>

| Backend | List endpoint | Extended endpoint / fields read |
|---|---|---|
| llama.cpp | `GET /v1/models` | `GET /props?model=<id>&autoload=0` — reads `default_generation_settings.n_ctx`, `modalities.vision`, `chat_template` (for thinking detection). Falls back to inline `meta.n_ctx`. Multi-preset router shape also scanned for `--ctx-size` / `--predict` argv. |
| litellm | `GET /v1/models` | Per-model `model_info` (or flattened top-level fields) — reads `max_input_tokens`, `max_output_tokens`, `mode`, `supports_function_calling`, `supports_vision`, `supports_reasoning`, `modalities.input` / `modalities.output`. Non-chat models (`mode !== "chat"`) are filtered out by default. |
| workbuddy-wild | `GET /v1/models` | Inline `context_length` and `max_output_tokens` on each model object. Enforces the `workbuddy/` or `traework/` model-id prefix (server rejects otherwise). |

When a backend doesn't expose a particular capability flag, the plugin falls back to **name-pattern heuristics** (`-vl`/`vision`/`llava` -> image input, `r1`/`o1`/`qwq`/`reasoning` -> reasoning, etc.), and finally to OpenCode's own defaults (tools=true, text+image input, 200K context, 32K output).

All three backends are registered under the `@opencode/ai/providers/openai-compatible` package, so chat-completion requests are routed to the correct baseURL with the configured Bearer token.

## Installation

### 1. Build

```bash
cd opencode-localcat
npm install
npm run build
```

This produces `dist/index.js`, which is the entry point the config below points at.

### 2. Wire it into OpenCode

Add the plugin to your `opencode.jsonc` (project or `~/.config/opencode/opencode.jsonc`). The `plugin` field is an array of specs; a spec is either a string or a `[spec, options]` tuple.

opencode resolves each spec with **no required `file://` prefix**. The accepted forms are:

| Spec form | Example | When to use |
|---|---|---|
| **npm package name** | `"opencode-localcat"` | Published/installed via `npm install` (incl. GitHub installs). |
| **npm spec, pinned** | `"opencode-localcat@1.2.3"` | Pin a version. |
| **relative path** | `"./opencode-localcat/dist/index.js"` | Local checkout, path relative to the config file. |
| **absolute path** | `"/abs/path/opencode-localcat/dist/index.js"` | Local checkout at a known absolute location. |
| **`file://` URL** | `"file:///abs/path/opencode-localcat/dist/index.js"` | Equivalent to an absolute path; optional. |
| **tuple w/ options** | `["opencode-localcat", { ... }]` | Any of the above plus options. |

The only thing that matters is that the resolved module exports the plugin. `file://` is just one valid form — it is **not** required.

### 3. Run

Start at least one backend (e.g. workbuddy-wild listening on `127.0.0.1:7863`), then run `opencode`. In the TUI:

- `/providers` should list `llama-cpp`, `litellm`, `workbuddy-wild` (only those whose backend is up).
- `/models` lists every discovered model with correct context/output limits and inferred capabilities.
- Pick a model (e.g. `/model workbuddy-wild/workbuddy/hy3`) and chat as usual.

Discovery runs once, when opencode loads its config. The opencode 1.x plugin API has no live-reload hook, so to pick up models added to a backend after opencode started, or to apply source changes, rebuild and restart opencode:

```bash
npm run build
# then restart opencode
```

## Configuration reference

All options live under the plugin tuple's second element in `opencode.jsonc` (i.e. `["<spec>", { ...options }]`). There are no environment variables — every value is explicit in the config file.

| Option | Type | Default | Description |
|---|---|---|---|
| `backends` | `object` | `{}` | Per-backend config. Keys: `llama-cpp`, `litellm`, `workbuddy-wild`. |
| `backends.<id>.baseURL` | `string` | (per backend) | OpenAI-compatible base URL including `/v1` suffix. Defaults: `http://127.0.0.1:8080/v1` / `:4000/v1` / `:7863/v1`. |
| `backends.<id>.apiKey` | `string` | (per backend) | Bearer token. llama.cpp defaults to `"no-key-required"`; LiteLLM and workbuddy-wild require a real key. |
| `backends.<id>.enabled` | `boolean` | `true` | Set `false` to skip a backend without removing its config block. |
| `backends.<id>.timeoutMs` | `number` | `5000` | Per-request timeout for `/v1/models` and any extended endpoints. |
| `backends.<id>.headers` | `object` | `{}` | Extra HTTP headers merged onto every discovery request. |
| `backends.<id>.reasoningField` | `string` | `"reasoning_content"` | Field in each streamed chat delta carrying reasoning tokens. Set it to the exact field your backend streams thinking under (e.g. `"reasoning"`, `"reasoning_text"`, `"thinking"`) so opencode aggregates the trace into one block instead of rendering each token as a separate "Thought" block. Applied to **every** model of a reasoning-capable backend; harmless for non-reasoning models. Override per-model via `backends.<id>.models.<modelID>.reasoningField`. |
| `backends.<id>.models.<modelID>.reasoningField` | `string` | *(inherits backend default)* | Per-model override of the reasoning field. Use when different models on the same backend stream reasoning under different field names. Unknown model IDs are ignored. |
| `backends.litellm.includeNonChat` | `boolean` | `false` | Include models whose `mode` is `embedding`/`completion`/etc. in the list. |

## Per-backend notes

### llama.cpp

- Default port `8080`. Started with `llama-server -m model.gguf --host 0.0.0.0 --port 8080`. Add `--api-key X` if you want authentication (then set `apiKey: "X"` in options).
- The plugin probes `GET /props?model=<id>&autoload=0` per model with a 1.5s timeout. `autoload=0` means **the model is not loaded** — the probe just reads the preset's metadata. 404s on `/props` (older builds without that endpoint) are silently ignored; capability falls back to inline `meta.n_ctx` and name heuristics.
- Multi-preset routers (multiple models exposed via one server) are supported — the plugin scans each preset's `status.args` for `--ctx-size`/`-c` and `--predict`/`-n`/`--n-predict`.
- Thinking/reasoning detection reads `default_generation_settings.chat_template` and matches the same markers llama.cpp itself keys on (`enable_thinking`, `reasoning_content`, `<think>`, `[THINK]`, `<|channel|>analysis`, `<|channel|>thought`).

### LiteLLM

- Default port `4000`. The plugin reads `model_info` either nested (`data[].model_info`) or flattened onto the model object — both shapes produced by different LiteLLM proxy versions are handled.
- Non-chat models (`mode: "embedding"`, `"completion"`, `"audio_transcription"`, `"rerank"`, etc.) are filtered out by default. Set `includeNonChat: true` to keep them.
- `supports_audio_input`/`supports_audio_output` are mapped to the `audio` modality; LiteLLM's `"speech"` modality is normalized to `"audio"` to match OpenCode's vocabulary.

### workbuddy-wild

- Default port `7863` (the Go proxy `workbuddy-wild`).
- **Model IDs must use the `workbuddy/` or `traework/` prefix** (e.g. `workbuddy/hy3`, `traework/DeepSeek-V4-Flash`). The server rejects prefix-less names with HTTP 400. The plugin also filters prefix-less ids defensively at discovery time so they never appear in `/models`.
- The `/v1/models` response from workbuddy-wild already carries `context_length` and `max_output_tokens` inline on each model, so no extra endpoint probe is needed.
- workbuddy-wild does **not** expose `supports_function_calling` / `supports_vision` / `supports_reasoning` flags. Capabilities beyond context/output limits come from the plugin's name heuristics (e.g. `hy3` -> reasoning=true, `DeepSeek-V4-Flash` -> reasoning=true).

## Troubleshooting

**A backend doesn't show up in `/providers`.**
- Check the OpenCode log for `[local-models] <id> offline: <error>`. The most common cause is the backend not running or listening on a different port.
- Verify with `curl`: `curl -H "Authorization: Bearer <apiKey>" <baseURL>/models` should return a JSON list.

**Models show up but with wrong context/output limits.**
- For llama.cpp: check `curl <baseURL without /v1>/props` — the `default_generation_settings.n_ctx` there is what the plugin reads. If it's `0` or `512` you started the server without `--ctx-size`.
- For LiteLLM: check `curl <baseURL>/models` and inspect the `model_info` block per model — the proxy only includes fields it knows about, so a model LiteLLM hasn't seen before will fall back to the plugin defaults (200K context, 32K output).
- For workbuddy-wild: the limits come straight from `/v1/models`'s `context_length` / `max_output_tokens`. If those are `0` or missing, the server didn't fill them in for that model.

**A model appears in `/models` but chat calls fail with `400 invalid_model`.**
- workbuddy-wild: confirm the model id has the `workbuddy/` or `traework/` prefix. The plugin filters prefix-less ids, but if you've configured the model elsewhere (e.g. directly in `opencode.jsonc`'s `provider` section) that bypasses the plugin's filter.

**Reasoning/thinking renders as one block per token (lots of tiny `Thought` lines).**
- This happens when a backend streams **empty placeholder fields** on every delta — most commonly `"tool_calls": []` (often alongside `"content": ""`, `"function_call": null`, `"refusal": ""`, `"extra_fields": null`). opencode's bundled `@ai-sdk/openai-compatible` parser treats a *present* `tool_calls` key as a tool call (`delta.tool_calls != null`), and an empty array `[]` satisfies that check: it closes the open reasoning block before each subsequent delta, so every 1-2 token reasoning chunk becomes its own `Thought`.
- workbuddy-wild's `workbuddy/*` models hit this because that path passes the upstream OpenAI stream through verbatim. The `traework/*` path rewrites the stream and only emits non-empty fields, which is why it aggregates correctly.
- The plugin installs a custom `fetch` on each provider (`provider.<id>.options.fetch`, forwarded by opencode to `createOpenAICompatible`) that strips these empty placeholder fields before the parser sees them, so reasoning aggregates into one block regardless of backend. No configuration is required.
- `backends.<id>.reasoningField` (default `"reasoning_content"`) remains available for the *separate* case where a backend streams thinking under a non-standard key (e.g. `"reasoning"`, `"reasoning_text"`, `"thinking"`) and is replayed on the request side. Override per-model via `backends.<id>.models.<modelID>.reasoningField`.
- To confirm what your backend streams, watch the raw SSE: `curl -N -X POST <baseURL>/chat/completions -H "Authorization: Bearer <key>" -H "Content-Type: application/json" -d '{"model":"<id>","stream":true,"messages":[{"role":"user","content":"hi"}]}'` and look at the keys inside each `delta`.

**A newly added backend model doesn't show up.**
- Discovery runs once at config load. Restart opencode to re-run it.

**The plugin fails to load entirely.**
- Run `npm run build` and confirm `dist/index.js` exists.
- Check the spec in your `opencode.jsonc` — it must resolve to the built entry. Either use the npm package name (`"opencode-localcat"`) or a path/URL to `.../opencode-localcat/dist/index.js` (relative `./...`, absolute `/...`, or `file:///...` all work).
- After rebuilds, restart opencode so it picks up the new code.

The plugin uses the opencode 1.x plugin API (`export default { id, server }`). The `server(ctx, options)` function returns a `config` hook. In `opencode.jsonc` the plugin is referenced by package name (`"opencode-localcat"`) or by a path/URL to the built entry — the loader resolves whichever spec form you supply. The hook:
1. Receives `options` (the tuple's second element) as its second argument.
2. Calls `discoverAll(opts)` — one `DiscoveredProvider` per enabled backend, with failures becoming offline records (not exceptions).
3. Converts each online backend to a `provider.<id>` config block (`toProviderConfig`) and assigns it onto `config.provider`.
4. Caches the discovery result in-process, so repeated config-hook invocations don't re-probe the backends.

Capability precedence, highest to lowest:
1. Extended-endpoint metadata (`/props`, `model_info`, `context_length`/`max_output_tokens`).
2. Name-pattern heuristics (`capabilities.ts`).
3. opencode's defaults for unknown models (tools=true, input=[text], ctx=200K, output=32K).
